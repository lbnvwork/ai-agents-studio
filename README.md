# ai-agents-studio — единый источник настроек агентов (Cline)

Готовый каркас «системы управления агентами» для команды ИИ-агентов (Cline), работающих в нескольких клонах проекта. Решает главную боль: **скиллы, правила и роли живут в одном месте, а не дублируются по N клонам**. Ядро нейтрально (плейсхолдеры), проектная специфика — в профилях, состав команды — данные, а не код.

## Проблема, которую решаем

Когда у каждого агента свой клон репозитория, а скиллы (`skills/`) и правила (`.clinerules/`) лежат внутри каждого клона — это N копий. Любая правка требует обновить все копии, иначе агенты работают по разным версиям правил (в нашей практике рассинхрон появился уже через пару дней).

## Решение

Настройки живут в **отдельном репозитории** `ai-agents-studio`; подключение к клонам — через **симлинки и копии** (скрипт `setup.sh`), без `git submodule`. Правка в ядре → агенты видят её (глобальные скиллы — сразу, правила и ролевые скиллы — после `setup.sh`).

## Структура

```
ai-agents-studio/
├── skills/                       # скиллы Cline (глобальные + по дорожкам)
│   └── <name>/SKILL.md
├── clinerules/                   # общие правила (10-git … 50-dod)
├── roles/<код>/00-role.md        # карточка агента (по коду агента)
├── profiles/                     # профили проектов
│   ├── _template/project.env.dist        # шаблон (в git)
│   └── <project>/project.env             # рабочие значения (НЕ в git)
│       ├── skills/<скилл>[.<код>|.<дорожка>].md   # переопределение скилла
│       └── roles/<код>.md                          # переопределение карточки
├── hooks/                        # скрипты-хуки Cline (экономия токенов)
├── setup.sh                      # развёртывание: рендер плейсхолдеров + симлинки
└── README.md
```

## Модель: агент и дорожка

| Сущность | Что это | Где живёт |
|---|---|---|
| **Агент** | единица идентичности: каталог-клон, код, своя карточка, свой канал комментариев, **свой стек** (docker-проект + порты) | `AGENTS`, `AGENT_*`, `PORT_*` в профиле; `roles/<код>/00-role.md` |
| **Дорожка (lane)** | пул одной компетенции: **ёмкость**, очередь, маршрутизация задач, набор скиллов | `LANES` в профиле; дефолты скиллов — `CORE_LANE_SKILLS` в `setup.sh` |

Ёмкость дорожки = ёмкость × число её агентов. Двое девов на **одном стеке** → одна дорожка (`dev:14` → 28 чел-дней). Разные платформы/стеки → **разные дорожки** (`backend:14` и `mobile:14`): задачи не взаимозаменяемы, маршрутизация идёт по дорожке.

Примеры: в проекте A два веб-разработчика → `dev` (2 агента, 28); в проекте B бэкендер и мобильный разработчик → `backend` (14) и `mobile` (14), а сводка «разработка» собирается группой дорожек.

## Профили проектов

| Файл | В git | Назначение |
|---|---|---|
| `profiles/_template/project.env.dist` | да | шаблон с комментариями по каждому ключу |
| `profiles/<project>/project.env` | **нет** (`.gitignore`) | рабочие значения: пути, репозитории, состав, docker, порты, план, ёмкость |

Ключи (подробнее — в шаблоне):

- **идентификация:** `PROJECT`, `PROJECT_TITLE`, `PROJECT_KIND` (`web`/`mobile`);
- **клоны:** `AGENTS_ROOT`, `AGENT_PREFIX`;
- **состав:** `AGENTS="каталог:код:дорожка …"` (порядок = порядок в конвейере);
- **дорожки:** `LANES="дорожка:ёмкость на агента:название …"`;
- **подписи и стек агента:** `AGENT_TITLE_<КОД>`, `AGENT_SHORT_<КОД>`, `AGENT_DOES_<КОД>`, `AGENT_STEM_<КОД>` (docker-проект `DOCKER_PREFIX_<стем>`, порты `PORT_<СТЕМ>_APP|DB|WEB`);
- **скиллы:** переопределения `LANE_SKILLS_<ДОРОЖКА>` / `AGENT_SKILLS_<КОД>` (дефолты дорожек — в ядре);
- **репозитории:** `CODE_REPO`/`CODE_REPO_URL`/`CODE_BRANCH`, `DOCS_REPO`/`DOCS_REPO_URL`/`DOCS_BRANCH`, `PM_DIR`;
- **docker и стенды:** `DOCKER_PREFIX`, `DOCKER_PM`, `DOCKER_DEV`, `DOCKER_PROD`, `PROD_DATA_DIR`, `PORT_DEV_*`, `PORT_PROD_*`;
- **план:** `CUR_SPRINT`, `SPRINT_FROM`/`SPRINT_TO`, `STAGES`, `DEADLINE_D1`/`DEADLINE_D2`;
- **ёмкость:** `SPRINT_DAYS`, `CAP_*`.

**Переопределения контента** (когда совет проекта не совпадает с ядром): скилл — `profiles/<project>/skills/<скилл>.<код>.md` → `.<дорожка>.md` → `.md`; карточка — `profiles/<project>/roles/<код>.md`. Ядро при этом не меняется.

## Где что живёт: студия, проект, слой

| Уровень | Что там | Где | Как обновляется |
|---|---|---|---|
| **Студия (ядро)** | правила, общие скиллы, модель агент/дорожка, `setup.sh`, toolkit, hooks | `ai-agents-studio` (public) | правится один раз → доезжает до всех проектов |
| **Проектный слой** | профиль проекта + переопределения (карточки агентов, варианты скиллов) + **проектные скиллы** | отдельный репозиторий проекта, напр. `<project>-agents` (private) | своя история версий, ядро не мусорит |
| **Форк ядра** | если человек строит **свою студию** (свои правила/процессы) | его форк `ai-agents-studio` | живёт своей жизнью — это нормально |

Запуск с проектным слоем:

```bash
git clone git@github.com:<org>/<project>-agents.git
./setup.sh --layer /path/to/<project>-agents            # профиль и переопределения — из слоя
./setup.sh --layer /path/to/<project>-agents --check    # дрейф
```

Порядок поиска контента (скилл/карточка): **слой** → профиль в ядре (`profiles/<project>/`) → ядро.
Промоушен скилла в ядро: если скилл не содержит проектных имён и команд — переносится в `skills/` одной правкой и сразу доступен всем проектам.

## Как добавить агента

1. Склонировать каталог агента (`AGENTS_ROOT/<префикс><имя>`) и добавить в `AGENTS` строку `<каталог>:<код>:<дорожка>`.
2. Завести подписи `AGENT_TITLE_/SHORT_/DOES_<КОД>` и, если нужен свой стек, `AGENT_STEM_<КОД>` + `PORT_<СТЕМ>_*`. Агент без стека (юрист, безопасник) — ключи портов не заводим.
3. Карточка: ядро (`roles/<код>/00-role.md`) или своя в `profiles/<project>/roles/<код>.md`.
4. `./setup.sh --project <project>`. Всё — код ядра не меняется.

**Минимальный состав:** РП + один разработчик + тестер + DevOps. Лид, аналитик, второй дев, доп. дорожки — добавляются строками в профиль по мере надобности; для отсутствующей дорожки задачи по смыслу уходят fallback-исполнителю (`LANE_FALLBACK_*`, использует toolkit).

## Как это работает

| Что | Механизм | Почему |
|---|---|---|
| **Глобальные скиллы** — `git-workflow`, `sync-env`, `write-instruction` | симлинки: `<агент>/.cline/skills/<skill>` → `ai-agents-studio/skills/<skill>` (+ `~/.cline/skills`) | Cline следует симлинкам директорий → обновления видны мгновенно |
| **Правила, карточка, ролевые скиллы** | копии с рендером плейсхолдеров | Cline **не** следует симлинкам файлов; рендер подставляет значения профиля |

Плейсхолдеры: `{{PROJECT}}`, `{{AGENT_DIR}}`, `{{AGENT_TITLE}}`, `{{AGENT_SHORT}}`, `{{AGENT_DOES}}`, `{{SKILLS_LIST}}`, `{{LANE}}`, `{{LANE_RU}}`, `{{LANE_CAP}}`, `{{DOCKER_PROJECT}}`, `{{PORT_APP}}` … — полный список и подстановка — в `setup.sh` (функция `render`).

## Скиллы: дефолты по дорожкам

| Дорожка | Скиллы (кроме глобальных) |
|---|---|
| `pm` (РП) | review-code, status-briefing, find-dead-code |
| `analytics` | — |
| `lead` | run-tests, explain-db, write-aquarium, write-adr, review-code, find-dead-code |
| `dev` | run-tests, explain-db, write-aquarium, find-dead-code |
| `test` | run-tests, make-postman, write-e2e-scenario |
| `devops` | run-tests, release, find-dead-code |

Списки — `CORE_LANE_SKILLS` в `setup.sh`; профиль перекрывает их (`LANE_SKILLS_*`, `AGENT_SKILLS_*`). Новая дорожка ядро не требует: набор задаётся в профиле.

## Установка

```bash
git clone git@github.com:<org>/ai-agents-studio.git
cd ai-agents-studio
cp profiles/_template/project.env.dist profiles/<project>/project.env   # заполнить под проект
./setup.sh --project <project>                    # применить
./setup.sh --project <project> --dry-run          # посмотреть, что изменится
./setup.sh --project <project> --check            # проверить дрейф (ничего не пишет)
./setup.sh --project <project> --only <каталог агента>   # точечно (пилот)
```

Если рабочий профиль в `profiles/` **один**, `--project` можно не указывать — `./setup.sh` возьмёт его автоматически. Профилей 0 или 2+ — скрипт скажет, что делать.

## Второй проект на той же машине (проектный слой)

Ядро обслуживает сколько угодно проектов: проектные данные не обязаны лежать в ядре — их можно
держать в **отдельном приватном репозитории слоя** (`<project>-agents`) и подключать ключом `--layer`.

```bash
# 1. Разложить клоны агентов (имена каталогов и корень — из профиля слоя)
cd /home/max/work/lazurit/projects/meddrive
for d in pm-jan analyst-feb lead-apr dev-may dev-jun tester-mar devops-jul; do
  mkdir -p "$d" && git clone git@github.com:<org>/<project>.git "$d"
  git clone git@github.com:<org>/<project>-docs.git "$d/docs"
done
git clone git@github.com:<org>/<project>-agents.git agents        # проектный слой — рядом с клонами

# 2. Развернуть правила, скиллы и toolkit по слою проекта
cd /home/max/work/ibs/projects/ibs-agents
./setup.sh --layer /home/max/work/lazurit/projects/meddrive/agents
./setup.sh --layer /home/max/work/lazurit/projects/meddrive/agents --check   # дрейф
```

Что делает `--layer`: берёт `project.env` (и переопределения `roles/`, `skills/`) из каталога слоя,
раскладывает в каждый клон `.clinerules/`, `.cline/skills/`, конфиг `.agents` и toolkit-скрипты в
`docs/09-Служебное/Скрипты/`. В `.agents` при работе со слоем пишется и путь к слою:

```
CORE=/home/max/work/ibs/projects/ibs-agents
PROJECT=med-drive
LAYER=/home/max/work/lazurit/projects/meddrive/agents
```

Готовый пример: проект **MedDrive** — клоны в `~/work/lazurit/projects/meddrive/` (слой — `agents/`),
доки `med-drive-docs` (структура хранилища, регламенты и витрины — те же, что у любого проекта на ядре).

Порядок для нового проекта: сначала профиль и клоны, потом `setup.sh --layer` (правила появятся
сразу), затем первый коммит доков — после него `setup.sh --layer` ещё раз, чтобы toolkit лёг в
клоны, где `docs/` пустой. Стек проекта описывается в слое: `skills/run-tests.md`,
`skills/find-dead-code.md` — ядро при этом не меняется.

## Команда «синхронизируйся» (скилл sync-env)

После сжатия памяти (компрессии) агенты «забывают» контекст. Скилл `sync-env` по команде **«синхронизируйся»** восстанавливает его:
1. `git pull` код (`develop`) и docs (`main`);
2. перечитывает правила `.clinerules/` и скиллы;
3. перечитывает план/статус (дашборд руководителя, детальный план, шапка спринта, Канбан, решения и риски);
4. перечитывает регламенты (`09-Служебное/Регламенты/`);
5. выдаёт сводку «что изменилось / что делать».

## Обновление настроек

1. Правка в `ai-agents-studio` → коммит → пуш.
2. Глобальные скиллы (симлинки) — агенты видят сразу (перезапуск Cline).
3. Правила, карточки и ролевые скиллы (копии) — `./setup.sh --project <project>`, затем `--check` для контроля дрейфа.

## Хуки Cline (экономия токенов)

Скрипты в `hooks/`. Главная идея — «внешняя память» агента, которая переживает компрессию контекста.

**Единственный безопасный хук с `additionalContext` — `PreCompact`** (срабатывает редко, только перед сжатием; выведенный конспект попадает в summary, а не накапливается):

```
событие: PreCompact
команда: bash /путь/к/ai-agents-studio/hooks/context-summary.sh
```

`context-summary.sh` читает `.cline/context.md` (его пишет скилл `sync-env`) и выводит первые ~300 символов — после сжатия это остаётся в summary.

**Не вешать `additionalContext` на частые события** (`UserPromptSubmit`, `PostToolUse`, `TaskResume`) — контекст раздуется по кругу.
