# sec-threat-model — модель угроз и поверхность атаки

## Триггер

**Каждый GitHub Release** проекта (не каждый выкат на контур). Плюс внепланово: новая интеграция,
новая роль/права, новый канал передачи данных, инцидент.

## Порядок

1. **Что изменилось** — дифф релиза: новые эндпоинты, интеграции, поля, роли, зависимости (из SBOM).
2. **Активы** — что защищаем: данные пациентов/пользователей, учётные записи, ключи, целостность данных, доступность.
3. **Границы доверия и потоки данных** — что пересекает границы (браузер ↔ API ↔ БД ↔ внешние сервисы ↔ мессенджеры).
4. **STRIDE по элементам** — Spoofing, Tampering, Repudiation, Information disclosure, DoS, Elevation of privilege;
   для каждой угрозы: сценарий · вероятность · влияние · существующая мера · остаточный риск.
5. **Поверхность атаки** — перечень: эндпоинты, аутентификация/авторизация, роли, загрузка файлов, каналы ПДн,
   внешние интеграции, админ-функции, фоновые задачи.
6. **Дифф с прошлым релизом** — «было/стало»: какие угрозы добавились, какие меры закрыли старые, что осталось.
7. **Запись** — обновить файлы проекта и журнал релиза.

## Артефакты (в проекте)

- `<проект>/docs/07-Безопасность/Модель угроз.md` — активы, границы, STRIDE, остаточные риски.
- `<проект>/docs/07-Безопасность/Поверхность атаки.md` — перечень точек входа, с датой и версией релиза.
- Строка в журнале релиза: «модель угроз обновлена · vX.Y.Z · новых угроз: N · закрыто: M».

## Правила

- Модель угроз — **живой документ**: дата и версия релиза в шапке, история изменений внизу.
- Не «переписываем заново» каждый релиз: обновляем и сохраняем дифф (иначе не докажешь динамику).
- Без модели угроз релиз не закрывается (гейт в release-чек-листе).
- Персональные данные в модели не фигурируют: оперируем категориями данных, а не людьми.
