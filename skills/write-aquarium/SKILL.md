# Аквариум — как это работает и что получится на наших данных

**Триггер:** руководитель говорит «делай пулрек, пиши аквариум» (или «пиши аквариум»).
**Момент:** конец разработки, **после всех коммитов в ветке**, до создания PR.
**Место:** **чат**. В статью задачи и в тело PR не дублируется.

## Зачем он нужен

Руководитель должен понять, **что произойдёт с нашими данными**, не читая код. Поэтому аквариум —
это алгоритм и трассировка, а не описание диффа.

## Структура (1–3 обязательны, 4 — если есть границы)

1. **Что делает** — 2–5 строк: назначение и место в системе.
2. **По блокам или файлам** — для каждого изменённого файла (или логического блока большого файла):
   - **Алгоритм** — нумерованные шаги по-русски: откуда берём данные → что проверяем → что делаем
     при каком условии. Смысл, а не синтаксис.
   - **Трассировка на наших данных** — конкретные значения: что в конфиге/на входе → что получится
     на выходе. Обязательно ветки: «если конфига нет», «если упало», «если DRY_RUN».
3. **Тонкости и ловушки** — что неочевидно и где легко ошибиться. Пример: метка антифлуда пишется
   до отправки, поэтому при сбое SMTP повторной попытки в течение часа не будет.
4. **Чего сознательно не делает** — для скриптов и фич с границами: список «не проверяет / не умеет»
   с причиной, чтобы не спрашивали «а почему нет X».

## Бюджет

- Блоков ≤ 8; шагов в алгоритме ≤ 7 на блок; трассировка ≤ 10 строк на блок.
- Больше — значит изменение слишком широкое (вопрос к Лиду), а не повод писать длиннее.

## Так надо (эталон, сокращённо)

### Шаг 2. Загрузить настройки
**Алгоритм:** 1) взять путь: `VPS_HEALTH_CONF` или `/etc/vps-health.conf`; 2) файл есть — выполнить его
в текущем shell; 3) пройти по настройкам: не задана или пуста → подставить дефолт.
**Трассировка:** `CONF=/etc/vps-health.conf` → файл есть → `MAIL_TO=…`, `DISK_WARN=80`,
`CONTAINERS="php messenger-worker …"` → дефолты не меняются (кроме `DRY_RUN=0`, его в конфиге нет).
Если конфига нет — скрипт работает на дефолтах.

### send(key, subj, body) — письмо с антифлудом
**Алгоритм:** 1) `_now` = секунды; 2) файл состояния `last-<key>`; 3) прошло < COOLDOWN → лог skip,
выход; 4) записать метку; 5) собрать тему (`SUBJECT_TAG HOST_TAG: subj`), base64 RFC 2047;
6) собрать MIME; 7) `DRY_RUN=1` → только лог; 8) иначе msmtp, лог sent/FAILED.
**Трассировка:** nginx down → `problems=2` → `send alert "проблем: 2"` → файла `last-alert` нет →
пишем `1763040334` → тема «[VPS][bloodcontrol] bloodcontrol: проблем: 2» → msmtp → «sent: проблем: 2».

## Так не надо

| Стр. | Что |
|---|---|
| 46–52 | если now − last < COOLDOWN → return |
| 53 | printf … > "$_state" |

Построчная таблица ничего не объясняет: не видно ни смысла, ни того, что получится на наших данных.

## Запрещено

Номера строк, пересказ диффа, журнал работ, номера коммитов, отчёты `СДЕЛАНО/ФАЙЛЫ`, логи прогонов.

## Чек-лист

- [ ] Понятно, что произойдёт на наших данных (есть трассировка с реальными значениями).
- [ ] По каждому изменённому файлу/блоку есть алгоритм шагами.
- [ ] Показаны ветки: нет конфига / ошибка / отладочный режим.
- [ ] Есть тонкости и раздел «чего не делает» (если применимо).
- [ ] Нет номеров строк и пересказа кода.
