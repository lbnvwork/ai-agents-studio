# Find-dead-code (мёртвый код: живёт только для тестов)

## Правило
**Если символ используется только тестами — это мёртвый код, его надо удалить.** Тесты **не являются обоснованием** существования продуктивного кода: тест проверяет поведение, а не создаёт спрос на API. Появилось «удобно для теста» — переписать тест, а не тянуть код в прод.

Проверка обязательна **в двух точках**: перед созданием PR (дев) и при ревью (лид). Проверяются **все символы из дифа задачи** (новые и изменённые), а не только новые файлы.

## Порядок проверки (5 шагов)
1. **Собери кандидатов из дифа** — символы, которые задача добавила/изменила (`git diff develop...HEAD`, фильтр по объявлениям классов/функций/констант для языка проекта).
2. **Найди использования ВНЕ тестов** — `grep` по имени символа с исключением тестового каталога и вендорной папки. Это ключевой шаг: символ, найденный только в тестах, — кандидат на удаление.
3. **Учти фреймворк-магию** (см. «Что НЕ мёртвый код») — если символ регистрируется конфигом/атрибутом/манифестом, `grep` по имени его не найдёт, и это НЕ мёртвый код.
4. **Вердикт по каждому кандидату:** `мёртвый` (удалить) / `живой` (есть вызов в прод-коде) / `фреймворк/внешний API` (оставить, зафиксировать почему).
5. **Оформи**: удалил — коммит `<код> ref убрать мёртвый код: <что>`; не удалил (исключение) — одна строка в отчёте/PR, почему оставлено.

## Вариант скилла под стек проекта
Команды поиска и доступные анализаторы у каждого стека свои — их держат в проектном слое (порядок поиска как у остальных скиллов):
`<слой>/skills/find-dead-code.<код агента>.md` → `find-dead-code.<дорожка>.md` → `find-dead-code.md`.
Дорожкой обозначают и стек: `find-dead-code.backend.md`, `find-dead-code.mobile.md`.
В варианте фиксируются: команды `grep` под структуру репо, какие анализаторы unused уже есть, а что проверяется вручную, и ускорители (скрипты-однострочники).

## Что НЕ мёртвый код (легальные исключения)
- **Тест-дубли и фикстуры:** `Fake*`, `Stub*`, `*TestDouble`, `fixtures/`, `tests/**` — созданы для тестов, так и задумано.
- **Точки входа фреймворка:** команды, слушатели событий, хендлеры очередей, контроллеры/процессоры, компиляторные расширения, компоненты, регистрируемые манифестом.
- **DI-теги и автоконфигурация:** сервисы, собираемые контейнером по тегу, — вызываются контейнером, а не прямым вызовом.
- **Ресурсы/сущности ORM:** вызовы генерирует фреймворк (геттеры/сеттеры, атрибуты-описания).
- **Публичный контракт по ТЗ:** API для внешних систем, точки расширения, заявленные в задаче/ТЗ — оставить, зафиксировать ссылку.
- **Профильные шимы/варианты:** реализации под профиль заказчика — используются сборкой по конфигу.
- **DTO/props для слота:** передаются блоком слота, ищи по имени ключа, а не по имени класса.

## Пример
Инвариант «нет профильных костылей»: флаг/метод существует только для инвариант-теста → в прод-коде 0 вхождений → символ удаляем, тест переписываем под реальный сценарий. Такой код в прод не тянем.
