# Release (релиз и версионирование)

Только DevOps. Версионирование — **SemVer с привязкой к плану**: `MAJOR.MINOR.PATCH` = `итерация.спринт.деплой`.

## Схема
- `MAJOR` = итерация: `0` сейчас → `1` альфа (20.11) → `2` бета.
- `MINOR` = номер спринта (из «Текущего спринта»): 3, 4, 5…
- `PATCH` = порядковый номер деплоя в спринте (авто-инкремент, руками не считать).

## Когда запускать
- **Колонка «Деплой»** канбана (между «Тестирую» и «Готово») — твой этап: выкатка на тестовый контур.
- При **каждом деплое** (после успешного мержа и выката на сервер).
- НЕ при каждом коммите/PR — только когда реально деплоим.
- После выкатки — отчёт в статью задачи (секция «Результат»: что выкачено, версия, ссылка); РП переводит карточку в «Готово».

## Как
```bash
scripts/release.sh <major> <minor> "описание релиза"
# напр.: scripts/release.sh 0 4 "спринт 4, задачи N.N–N.N"
```
Или: GitHub Actions → «Release» → Run workflow (major, minor).

## Что делает скрипт
1. Берёт последний тег `v<major>.<minor>.*`, делает PATCH +1 → новый тег `v0.4.1`.
2. Создаёт GitHub Release + строку в `CHANGELOG.md`.

## Откуда брать major/minor
- `minor` = номер текущего спринта (сейчас 4).
- `major` = `0` до альфы (20.11); после альфы `1`; после беты `2`.
- Смена `minor`/`major` — по отмашке руководителя (старт спринта / итерации).

## Проверка
- `git describe --tags --abbrev=0` — текущая версия.
- Версия видна в Sidebar (`v0.4.1`).
