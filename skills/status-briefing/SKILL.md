# Status-briefing (оперативный обзор / диспетчер)

Снимает переключение контекста руководителя: собрать картину по команде, актуализировать статусы и дать консультацию «что делать дальше».

## Шаги

1. **Git-состояние (и закоммиченное, и незакоммиченное):**
   - 7 клонов **docs** (`{{AGENT_PREFIX}}*/docs`): `git status -s` + `git diff --stat` — правки статей = отчёты агентов и ответы руководителя, которые ещё не закоммичены.
   - 7 клонов **кода** (`{{AGENT_PREFIX}}*`): текущая ветка + `git status -s` (незакоммиченный код).
   - клон РП `{{DOCS_REPO}}`: `git pull origin main` + `git status -s`.
   - **PR-ы (код):** `gh pr list` в клоне кода `{{PROJECT}}` — открытые PR, что на ревью, что ждёт мержа; сверь с ветками агентов (`git branch`).
2. **Прочитать:** `09-Служебное/Дашборд руководителя.md` (план + факт + загрузка команды: «Ждёт меня», «Ждут агентов», конвейер, застой, кандидаты на перенос) + `03-Задачи/Канбан.md` + шапки спринтов `03-Задачи/Планы спринтов/Спринт-NN.md` (цель/ёмкость/KPI) + `03-Задачи/Планы спринтов/Детальный план спринтов.md` (генерируется из данных; полный бэклог: оценка/порядок/цель→KPI) + `09-Служебное/Решения и риски.md`.
3. **Сверить каналы комментариев** статей — `## Комментарии: Имя (роль)` (новое сверху), **включая незакоммиченные файлы** в копиях агентов (незакоммиченная правка → ждёт коммита руководителя). Начинай с **«Контекста передачи»** (первая секция статьи) — это сжатое состояние задачи; в журнале досматривай только то, чего там нет.
4. **Обновить данные (витрины собираются сами):**
   - Канбан — передвинуть карточки (двигает только РП).
   - Статьи: `status`, `awaiting`, `updated` и «Контекст передачи» — четыре поля разом; при уточнении — оценку `est`.
   - Пересобрать витрины плана: `python3 09-Служебное/Скрипты/sprint_plan.py --write` (обновит `Детальный план спринтов.md` и AUTO-таблицы в шапках спринтов).
   - Проверки: `python3 09-Служебное/Скрипты/check_meta.py` + `sprint_plan.py --check`.
   - Решения, риски и вопросы, **не выводимые из данных**, — в `09-Служебное/Решения и риски.md`.
   - Незакоммиченные отчёты агентов помечать явно: «агент отчитался, файл не закоммичен → нужно ревью + коммит».
5. **Консультация:** что делать руководителю по приоритету: где блокеры (P1), где ждут **ревью + коммита** незакоммиченные отчёты, где ждут ответа агенты (по ответам руководителя в «Комментариях»), кого подтолкнуть, какие пуши ждут отмашки.
6. **Промты для агентов:** в финальном ответе прикладывай готовые промты — текст, который руководитель копирует и отправляет каждому агенту (триггер + что делать + к какой задаче).

## Правила

- Статусы в Канбане двигает только РП.
- Отчёты агентов и ответы руководителя могут быть **незакоммиченными** — это нормальный этап «отчитался → жду ревью/коммита».
- Ответы/решения руководителя — в его канале `## Комментарии: Макс (руководитель)` (в чат — только пинг). Учитывай их при сверке.
- Перед сводкой прогоняй: `python3 docs/09-Служебное/Скрипты/comments_feed.py --digest` (5 строк на задачу) и `check_meta.py` / `check_comments.py` по изменённым статьям (frontmatter, структура каналов, бюджет журнала).
- Если данных мало (агент не отчитался) — сказать явно, не додумывать.
- В финальном ответе всегда присылай промты для агентов (готовый текст запуска для каждого агента, кого нужно подтолкнуть или кому дать задачу).

## Актуализация статусов после мержа (триггер «смержил #N»)
1. Определи задачу по PR: `gh pr view <N>`.
2. Канбан — передвинь карточку: после тестирования → **«Деплой»** (DevOps выкатывает на тестовый контур, версия через скилл `release`); после его отчёта → **«Готово»** (приёмка руководителя на тестовом).
3. Обнови frontmatter `status:` в статье задачи (`testing → deploy → done`).
4. Пересобери витрины плана из данных: `python3 09-Служебное/Скрипты/sprint_plan.py --write` (статусы читаются из статей — руками дублировать не нужно).
5. Запиши **событие** в свой канал: `- ГГГГ-ММ-ДД ЧЧ:ММ МСК · Ян (РП) · [статус] …`, **перепиши «Контекст передачи»** статьи и обнови поле `awaiting` (кто держит следующий шаг).
6. При переводе в «Тестирую» — пинг **Тестеру и Аналитику** (сверка БЖ, если задача меняет правила; иначе пометка «БЖ-сверка: не нужна»).

## Перенос задачи в другой спринт (ОБЯЗАТЕЛЬНЫЙ чек-лист — «не забывать!»)
**Ключевое: при переносе задача получает НОВЫЙ номер (код) целевого спринта.** Перенос без нового номера — ошибка.
1. **Новый код** = `<спринт>.<следующий свободный NN>` (напр. `4.2 → 5.23`).
2. **Переименовать файл статьи** в `Спринт-NN/` с новым кодом; заголовок `# N.N.` внутри — тоже новый.
3. **Frontmatter**: `code`, `sprint`, `branch` (`5_23_...`), `depends_on` — на новые коды.
4. **Обновить все ссылки**: зависимости в других статьях, `depends_on`, статьи-разборы; таблица «Было → Стало» собирается из `carried_from`.
5. **План:** `carried_from` = старый код; в архиве — `done`/`cancelled` и реестр «Пройденные спринты».
6. **Проверка**: `grep -rn '<старый код>' docs/` (кроме пары «Было → Стало») + `sprint_plan.py --write`.

## Переход на новый спринт
1. Закрой спринт: реестр задач → `03-Задачи/Планы спринтов/Пройденные спринты/Спринт N.md` (образец — «Спринт 4»), в шапке спринта поставь `status: done`.
2. Заведи/обнови шапку нового спринта `Планы спринтов/Спринт-NN.md` (`goal`, `kpi`, `capacity`, `capacity_note`, даты, `status: current`).
3. Расставь `order` и `est` задачам целевого спринта; переносы — **новым кодом** + `carried_from`.
4. Пересобери витрины (`sprint_plan.py --write`) и прогони `check_meta.py` + `sprint_plan.py --check`.
