# Команды в терминале (рабочий режим агента)

Проверено 24.09.26 на машине РП (VS Code + Cline 4.1.20, Ubuntu, bash 5.2).

## Режим терминала — обязательная настройка

Cline → **Settings → Terminal → Terminal Execution Mode = «Background Exec»** (не «VS Code Terminal»).

Почему: в режиме «VS Code Terminal» Cline ждёт от терминала маркер завершения через shell integration. Если маркер до расширения не доходит, оно фиксирует `markCommandUnobserved` и уходит на `markerless_heuristic` (таймер). Следствия: результаты соседних команд склеиваются в один снимок экрана, вывод может принадлежать **другой** команде, коды возврата врут (`exit 1` на успешных командах), длинные команды читаются не до конца.

**Симптом сломанного режима:** в ответе на команду есть «Shell integration did not report command completion … captured with a timing heuristic» или вывод, который не соответствует отправленной команде.

**Что НЕ помогает (не тратить время):** настройки VS Code `terminal.integrated.*` (проверено: правка + `Developer: Reload Window` + kill всех терминалов — поведение не изменилось). Обновление расширения: 4.1.20 — последняя версия.

## `spawn /usr/bin/bash ENOENT` — мёртвый cwd, а не сломанный терминал

Симптом: любой вызов команды падает с `Failed to execute command: spawn /usr/bin/bash ENOENT`,
а `search_codebase` отвечает «Searched 0 files». При этом `/usr/bin/bash` и линковщик на месте.

Причина: Cline запускает команду с `cwd` = каталог **задачи** (workspaceFolder), а не процесса VS Code;
Node при `spawn` с несуществующим `cwd` отдаёт именно `ENOENT` — поэтому в тексте ошибки оказывается имя бинарника.
Типичный случай: каталог проекта переехал/переименован, а чат открыт старый.

**Что не помогает (не тратить время):** `Restart Extension Host`, перезапуск VS Code на старом пути,
переустановка bash. `cd <новый путь>` внутри команды — тоже: bash не стартует, `cd` не исполняется.

**Что помогает:**

1. Полностью перезапустить VS Code, открыв **новый** корень (`File → Open Folder…` через диалог, не Recent),
   и начать **новую** задачу — она получит валидный `workspaceFolder`.
2. Сохранить старый чат: вернуть старый адрес симлинком `ln -sfn <новый путь> <старый путь>`
   (если переехал весь корень проектов — шим из набора симлинков, см. стандарты студии).
3. Сверить в шапке задачи Cline «Environment / Working directory» с `pwd`: путь должен существовать.

Быстрая диагностика в терминале VS Code (он от Cline не зависит):

```bash
pwd; ls -d <путь из ошибки>; ls -1 ~/work
```

**Точный список мёртвых адресов** (какой `cwd` помнит каждая задача) — в базе Cline:

```bash
sqlite3 ~/.cline/data/db/sessions.db "select distinct cwd from sessions;" | while read -r p; do
  [ -d "$p" ] && echo "ЖИВ   $p" || echo "МЁРТВ $p"; done
```

`cwd` задачи менять нельзя (фиксируется при создании, в UI/настройках такого нет) — лечим адресом: `ln -sfn <новый путь> <старый путь>`.

## Проверка за 30 секунд («канарейки»)

```bash
echo "canary ok"                                             # должен вернуться своим выводом
sleep 8; echo "long ok"                                      # длинная команда — тоже
docker compose -p <проект> exec -T <сервис> sh -lc '<команда тестов>'  # реальная длинная (команды — в скилле run-tests)
```

Все три вернулись своими выводами — режим в порядке. Вернулся «общий снимок» или warning — проверить настройку из раздела выше.

## Docker: всегда указывать проект

В каталоге может быть несколько compose-проектов (например, у РП — личный стек и стенд приёмки; у студийных агентов стека нет). Обычно `-p` **не нужен**: проект берётся из `COMPOSE_PROJECT_NAME` в `.env` клона, поэтому команда одинаково работает у любого агента. Явный `-p` — только чтобы адресовать **чужой** проект из этого каталога. Имя своего проекта — в `.clinerules/00-role.md` или в `docker compose ls`.

```bash
docker compose ls                                                            # какие проекты подняты и из какого каталога
docker compose -p <проект> exec -T php sh -lc 'vendor/bin/phpunit'           # пример веб-стека: backend, workdir /var/www/html
docker compose -p <проект> exec -T node sh -lc 'npm test'                    # пример веб-стека: frontend, workdir /app
docker compose -p <проект> exec -T php sh -lc 'php bin/console cache:clear'   # после обновления кода без rebuild
```

Свои команды (стек проекта) — в скилле `run-tests`.

## Гигиена команд

- Неинтерактивно: `-T` для `docker exec`/`run`, `--no-pager` для git, `-y` / `--no-input` для пакетных менеджеров. В Background Exec терминал невидим: команда, ждущая ввода, повиснет молча.
- Одна команда = одно действие — читаемый дифф и отчёт. Пачка команд в одном вызове допустима только для быстрых независимых проверок.
- Не создавай ложных падений: `… || true`, `; echo "exit=$?"` — чтобы «нет совпадений» в `grep` не выглядело как ошибка.
- Локальный рантайм годится только для мелочей: сборка и тесты — в контейнере (локальная версия рантайма легко расходится с образом проекта).
