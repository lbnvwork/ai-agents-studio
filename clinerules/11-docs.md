# Правила документации

- Документация живёт в отдельном репо `{{DOCS_REPO}}` (НЕ в репо кода `{{PROJECT}}`). После переноса в репо кода папки `docs/` нет.
- `{{DOCS_REPO}}` — общий репо: у каждого агента в каталоге `docs/` — его клон; все имеют доступ и право пушить документацию.
- Обсидиан руководителя работает только из папки РП (`{{PM_DIR}}/docs/`).
- Правки документации агент **не коммитит**: правит файлы → присылает **название коммита** → руководитель коммитит → агент по отмашке пушит (свободно, **без PR**). Порядок и запрет коммитов — `20-workflow.md`.
- **Где что писать в статье задачи** (подробно — `docs/09-Служебное/Регламенты/Комментарии задач.md`):
  - «Контекст передачи» — РП, переписывает при каждой смене статуса (входящий читает его + постановку + 5 последних записей — этого достаточно);
  - каналы `## Комментарии: Имя (роль)` — каждый пишет только в свой, append-only, новое сверху, бюджет S10 / M20 / L40 строк на задачу (канала автора нет — `comment_stamp.py --write` создаст его в позиции по конвейеру);
  - дата и время записи — **фактические**, метку ставит `comment_stamp.py` (правила — раздел «Коммуникация» ниже);
  - отчёт по подзадаче и коммиту — в чат руководителю и в квитанцию коммита, **в статью не дублируется**;
  - «Аквариум» — таблица трассировки сценариев (не журнал), «Реализация» — сжатый итог ≤10 строк;
  - для задач `type: doc/infra/test` секции «Реализация» и «Аквариум» не создаются.
- Руководитель читает правки в Obsidian (папка РП `{{PM_DIR}}/docs/`).
- Именование и структура — по справочнику `docs/README` (завести при переносе).
- До переноса: документация ещё в этом репо — правки доку идут тем же порядком (отчёт → коммит руководителя, без PR).

## Студийные агенты в проекте (владение разделом)

У студийного агента в проектных доках — свой раздел по домену: «Юридическое» (юрист),
«Безопасность» (безопасник), «Клиническое» (медэксперт). Раздел — его зона: содержимое, структура,
версии, шапка файла (владелец · статус · источник · дата).
- Агент пишет **только в свой раздел** проекта; статьи задач не правит, карточки не двигает.
- РП, аналитик, Лид, Дев в чужой раздел не пишут — только замечание владельцу через задачу.
- Канон живёт в проекте (он уходит заказчику); в студии — реестр, вопросы, шаблоны и **ссылка** на канон.
- Ссылаемся **по названию** раздела, не по номеру папки: числовой префикс — только для сортировки,
  его может не быть, и в разных репозиториях он разный.
- **Единственное исключение по коммитам:** студийный агент коммитит и пушит сам, но только свой раздел —
  при установленном хуке `.git/hooks/pre-commit`, который отклоняет любые другие пути. Прочее — руководитель.

## Коммуникация руководитель ↔ агент
- Ответы/замечания/решения руководителя агентам — в «Комментарии» статьи задачи, с `→ <агент>`.
- В личный чат агенту — только короткий пинг-триггер: «оставил замечания в комментариях к S.NN» / «закоммитил». Агент, получив пинг, **обязан** открыть статью и прочитать комментарий.
- **Дата и время любой записи в канал/журнал — фактические, с рабочей машины.** Метку ставит `docs/09-Служебное/Скрипты/comment_stamp.py` (`--agent <код> --type <тип>`, при `--write` — запись сразу в свой канал «сверху» + `updated`, а если канала нет — создаст его по конвейеру); при ручной записи сверь время `date '+%Y-%m-%d %H:%M %Z'` (зона не МСК → привести к МСК). Запрещено: копировать дату из соседней записи, брать её из `updated`/шапки/имени файла, писать «вчерашнюю» дату. Ловушка: `check_comments.py` → «метка времени в будущем».
- Это даёт единый журнал переписки по задаче (отчёты агента + решения руководителя) — скилл `status-briefing` читает его целиком.

## Синхронизация окружения («синхронизируйся»)

По команде «синхронизируйся» / «обнови окружение» / «перечитай контекст» — скилл `sync-env`:
1. Код: `git fetch origin && git pull origin develop` (в своей ветке — merge `develop`). Docs: `cd docs && git pull origin main`.
2. Перечитать правила (свой `00-role.md` + `20-workflow.md`), регламенты `09-Служебное/Регламенты/`.
3. Перечитать план и статус: `09-Служебное/Дашборд руководителя.md`, `03-Задачи/Планы спринтов/Детальный план спринтов.md`, шапку своего спринта, `03-Задачи/Канбан.md`, `09-Служебное/Решения и риски.md`.
4. Прочитать **«Контекст передачи»** своей активной задачи — это вход в контекст вместо чтения всей истории.
5. Проверить доки по задаче: `check_meta.py` + `check_comments.py <статья>` (frontmatter, каналы, бюджеты).
6. Обновить конспект `.cline/context.md` (5–10 строк: текущая задача, статус, что дальше).

## Протокол записи в docs (обязательный ритуал — против конфликтов)

`{{DOCS_REPO}}` — общий `main` без веток: несколько агентов пишут параллельно в одни файлы. Поэтому запись в доки — строго по протоколу:

1. **Перед правкой** любого файла docs — `git pull origin main` (в своём клоне `docs/`). Без свежего `main` правку не начинай.
2. **Правь** файлы (в т.ч. отчёт в «Комментарии» задачи).
3. **Перед передачей названия коммита** руководителю — ещё раз `git pull --rebase origin main`; если конфликт — разреши его **сразу** (коммит с конфликтом не передавай).
4. **Пуш** — только как `git pull --rebase origin main && git push origin main`. `--force` / `--force-with-lease` запрещены.
5. **Короткое окно**: не копи правки docs — «отредактировал → сразу коммит-запрос → пуш». Файл не держи изменённым долго.
6. **Общие файлы** (Канбан, «Дашборд руководителя», «Детальный план спринтов», шапки `Спринт-NN`, «Команда и ёмкость», «Решения и риски», «Покрытие ТЗ (FUNC)») двигает только РП; агент в них не пишет (витрины генерируются скриптом `sprint_plan.py`). Чужую задачу не правишь без пинга её исполнителю. **План проекта = данные**: `est`/`order`/`goal` живут в статьях — регламент `docs/09-Служебное/Регламенты/План и данные.md`.

Аварийный fallback при конфликте: сохрани свой текст → `git pull --rebase` → разреши конфликт вручную → `git rebase --continue` → пуш.
