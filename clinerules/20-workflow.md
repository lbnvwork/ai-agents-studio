# Воркфлоу и статусы

- Конвейер: РП → Аналитик → Лид → Дев+Тест → Ревью(Лид) → Тест (**+ сверка БЖ Аналитиком**) → **Деплой (DevOps)** → Готово. Полная схема: `docs/09-Служебное/Регламенты/Воркфлоу.md`. Колонки канбана: Надо делать → **Анализ** (Феб+Эйп) → Делаю → Ревью → Тестирую (Дев, Марк, **Феб**) → **Деплой** (Юлий) → Готово (+Отложено/Отменено).
- Статусы задачи: `spec → planned → in_progress → review → testing → deploy → done` (+`blocked`, `cancelled`).
- WIP: 1–2 задачи в работе на агента.
- **Docker: по завершении задачи останови свой стек** — `docker compose -p <проект> down` (имя проекта — в `.clinerules/00-role.md` или `docker compose ls`; без `-p` команда уйдёт не в тот проект). RAM на машине ограничена (критично), не держи контейнеры без надобности.
- **Команды в терминале** (режим агента, `-p`, `-T`, канарейки проверки) — `21-terminal.md`.
- **ЗАПРЕТ КОММИТОВ АГЕНТАМ (критично, без исключений):** агент не выполняет `git commit` — ни в коде, ни в документации (`{{DOCS_REPO}}`). Коммит — только руководитель (или РП по доверенности). Пуш — агент по отмашке руководителя (`{{DOCS_REPO}}` — свободно, без PR; `{{PROJECT}}` (код) — в ветку + пулрек по отмашке).

## Отчёт вместо коммита (обязательный формат)
Полный отчёт агент пишет в «Комментарии» статьи задачи (docs).
**В чат руководителю агент отправляет ТОЛЬКО блок `КОММИТЫ`** (строки с названиями, копируются как есть). В чат РП — полный отчёт (при необходимости согласовать решение).

```
СДЕЛАНО:  <что сделано, кратко>
ФАЙЛЫ:    [код]  <путь в репо кода>
           [docs] <путь в репо доков>
БЛОКЕРЫ:  <есть/нет + что именно блокирует>
ЗАМЕТКИ:  <опционально — важное, но не блокирующее>
```

Отдельным блоком — **названия коммитов, по одной строке**:
```
[код]  N.N fix <что исправлено> (одна строка, без служебных пометок)
[docs] N.N doc <что изменилось в доках> (одна строка)
```
После блока — служебная строка вне него:
```
СТАТУС: жду отмашки — коммит и пуш делает руководитель.
```

### Правила блока КОММИТЫ (жёсткие)
- **В блоке — только названия коммитов.** Одна строка = один коммит; строка начинается с `[код]` или `[docs]`.
- **Внутри блока запрещены служебные пометки:** «(жду отмашки)», «(коммит/пуш за вами)», «(после ревью)», «TODO», «см. чат», пояснения в скобках, списки `- …`. Всё служебное — в поле `СТАТУС` (или `ЗАМЕТКИ`) **вне** блока.
- Название коммита — **законченная строка** формата `<код> <тип> <описание>` (типы — в `10-git.md`). Руководитель копирует её целиком и без правок; любая лишняя пометка уходит в `git log`.
- **Самопроверка перед отправкой:** если в блоке есть строка, не начинающаяся с `[код]`/`[docs]` — удали её.

> **Как НЕ надо:** писать внутри блока с названиями служебные пометки («жду отмашки…», «коммит/пуш за вами», «после ревью», «TODO») — они попадают в `git log`.


## Коммуникация руководитель ↔ агент
- Ответы/замечания/решения руководителя агентам — тоже в «Комментарии» статьи задачи, с `→ <агент>`.
- В личный чат агенту — только короткий пинг-триггер: «оставил замечания в комментариях к S.NN» / «закоммитил».
- Агент, получив пинг, обязан открыть статью задачи и прочитать комментарий руководителя.
- **Дата и время любой записи в канал/журнал — фактические, с рабочей машины.** Метку ставит `docs/09-Служебное/Скрипты/comment_stamp.py` (`--agent <код> --type <тип>`, при `--write` — запись сразу в свой канал «сверху» + `updated`, а если канала нет — создаст его по конвейеру); при ручной записи сверь время командой `date '+%Y-%m-%d %H:%M %Z'` (зона не МСК → привести к МСК). Запрещено: копировать дату из соседней записи, брать её из `updated`/шапки/имени файла, писать «вчерашнюю» дату в новую запись. Ловушка: `check_comments.py` → «метка времени в будущем».
- Это даёт единый журнал переписки по задаче (отчёты агента + решения руководителя) — скилл `status-briefing` читает его целиком.

## Статусы
- **Перевод в «Тестирую»:** РП пингует тестировщика **и Аналитика** (если задача меняет правила/поведение: feature/refactor, правила дозирования/триажа/согласия/классов препаратов, менялись «Бизнес-логика»/«Сценарии»). Аналитик даёт вердикт в секцию «Бизнес-логика (проверка Аналитика)» статьи задачи («соответствует» / «внесены правки БЖ» / «есть замечания к реализации») и при необходимости правит статьи `02-Аналитика/Бизнес-логика/`. Правил не меняет — РП помечает «БЖ-сверка: не нужна (причина)».
- **Колонка «Деплой» (между «Тестирую» и «Готово»):** после тестирования РП двигает карточку в «Деплой»; DevOps выкатывает на тестовый контур (версия через скилл `release`) и отчитывается в статью (секция «Результат»); РП двигает карточку в «Готово», где руководитель делает приёмку на тестовом. Статус `deploy` из модели наконец используется.
- **Канбан** — единственный источник истины. **Двигает только РП** (скилл `status-briefing`), атомарно, сразу после отчёта агента. Агент колонки не двигает — только отчитывается.
- **«План спринтов»** (планировщик) — обновляется РП **один раз в конце дня**, одним проходом.
- Не дублируй статус в 4 местах: статус живёт в Канбане, остальное — зеркала.
- Смена статуса — комментарием в статье задачи (`ГГГГ-ММ-ДД ЧЧ:ММ МСК · Кто · [статус] текст → кому`); пишет РП при движении карточки. Метка времени — фактическая: ставит скрипт `comment_stamp.py` (или `date '+%Y-%m-%d %H:%M %Z'` при ручной записи).
- **Ревью: замечания по коду — в PR** (inline/суммарно); в задачу — короткий статус («вернул на доработку, замечания в PR #N») + вердикт. Не дублируй подробности в задачу.
- Не раздувай задачу: существенная доработка = новая задача. Эскалация: Дев/Тест → Лид → РП → Руководитель.

## Перенос задачи в другой спринт — ЖЁСТКОЕ ПРАВИЛО (не забывать!)
**При переносе задача получает НОВЫЙ номер (код) целевого спринта.** Перенос без нового номера — ошибка процесса.
1. **Новый код** = `<спринт>.<следующий свободный NN>` (напр. `4.2 → 5.23`).
2. **Переименовать файл статьи**: `Спринт-04/4.2. Название.md` → `Спринт-05/5.23. Название.md`; заголовок `# N.N.` внутри статьи — тоже новый.
3. **Frontmatter**: `code`, `sprint`, `branch` (`5_23_...`), `depends_on` (ссылки на другие перенесённые задачи — на новые коды).
4. **Обновить все ссылки** на старый код: зависимости в других статьях, `depends_on`, статьи-разборы; таблица переносов «Было → Стало» собирается из `carried_from` автоматически.
5. **План:** `carried_from` = старый код + перенумерованный `order`; статья/строка закрывается в архиве (`done`/`cancelled`, реестр — «Пройденные спринты»).
6. **Проверка перед отчётом:** `grep -rn '<старый код>' docs/` (кроме пары «Было → Стало») + пересборка витрин `python3 09-Служебное/Скрипты/sprint_plan.py --write`.
