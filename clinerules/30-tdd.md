# TDD и тесты

- Тесты пишутся ДО реализации (TDD): сначала скелет теста, затем код до зелёного.
- После реализации — повторно пересмотри тесты: какие кейсы ещё покрыть, что изменилось, что устарело. Выводы — комментарием в статью задачи (секция «Тесты (TDD)»).
- Покрывай позитивные и негативные сценарии + security-сценарии (злоумышленник).
- **Docker: команды — из своего клона**, проект берётся из `.env` (`COMPOSE_PROJECT_NAME`), `-p` не нужен (явный `-p` — только для чужого проекта в этом каталоге). Имя проекта — в `00-role.md` или `docker compose ls`.
- **Прогон — одной командой проекта: `make ci`** (линтеры + тесты + сборка + метрики; та же точка входа в CI). Нет `make ci` — fallback по стеку из скилла `run-tests`, и это фиксируется в отчёте.
- Стек другой → вариант скилла в профиль: `profiles/<project>/skills/run-tests.<дорожка>.md` (ядро не меняется).
- **Тесты зелёные и `make ci` OK — обязательное условие перед коммитом/PR.** Результат — обязательное поле отчёта и PR: `make ci OK: 12 шагов, 184 с` или `make ci: упало 2 из 12 — phpstan, eslint`. «Пусть CI проверит» — не аргумент: CI лишь контрольная точка.
- **Линтеры и стиль — внутри `make ci`, жёсткий режим (fail, без warn).** Отдельно по линтерам не гоняем; любое замечание = красный прогон. **Новый код пишется сразу чисто** — долг не копим.
- **Тесты не оправдывают мёртвый код:** символ, используемый только тестами, удаляем, а тест переписываем под реальный сценарий. Проверка — скилл `find-dead-code` перед PR (дев) и на ревью (лид).
- E2E — инструментом проекта (ядро: пример Playwright; мобильное — Espresso/Appium), сценарии в `docs/05-Тестирование/Сценарии-E2E/`.
- Служебные команды, ждущие ввода, запрещены (`-T`, `--no-pager`, `-y/--no-input`) — в Background Exec такая команда повиснет молча (подробно — `21-terminal.md`).
